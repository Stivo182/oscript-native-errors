# Инструкции для агентов

## Назначение проекта

`native-errors` нормализует нативные исключения встроенных объектов OneScript
в коды библиотеки `errors`. Правила классификации находятся в `src/`, их
проверки в `tests/`, а исследовательские данные и инструменты в `probes/`.

Перед изменением изучи соседний код и существующие тесты. Не перезаписывай
чужие незакоммиченные изменения и не расширяй задачу без необходимости.

## Подготовка и проверка

- Установи зависимости командой `opm install -l --dev`, если их еще нет.
- Если в среде отсутствует OneUnit, установи его командой `opm install oneunit`.
- Обычная проверка проекта: `oneunit execute`.
- Проверка инструментов исследования: `oscript .\probes\probes.os test`.
- Перед завершением проверь только относящиеся к изменению команды, формат и
  отсутствие ошибок в diff. Полный регресс запускай по явному запросу или когда
  изменение затрагивает широкий контракт.

## Общий порядок работы

1. Проверь состояние рабочего дерева и выдели файлы, относящиеся к задаче.
2. Найди существующий аналог и соблюдай его структуру и терминологию.
3. Для нового правила сначала воспроизведи нативную ошибку, затем добавь
   положительный и близкий отрицательный сценарии.
4. Измени правило, тест и пользовательскую документацию, если меняется
   поддерживаемый код или его смысл.
5. Проверь минимально достаточный набор тестов.

## Исследование ошибок OneScript

Подробное описание команд, файлов данных и обновления снимков находится в
[`probes/README.md`](probes/README.md). Используй публичный CLI, а не внутренние
скрипты или удаленные PowerShell-обертки.

Начинай обычное исследование с:

```text
oscript .\probes\probes.os review next
```

### Исходники движка

1. Получи следующую сигнатуру:

   ```text
   oscript .\probes\probes.os review source --limit 1
   ```

2. Рассмотри только эту сигнатуру и зафиксируй решение в
   `probes/data/source-error-review.json`.
3. У записи обязательны `File`, `ExceptionType`, `Statement`, `Status`, `Code`
   и `Note`.

`source-error-report.json` создается командой `data refresh-source`. Не
перегенерируй его без обновления движка OneScript или явного указания
пользователя.

### Внешние .NET-вызовы

1. Получи следующую границу:

   ```text
   oscript .\probes\probes.os review external --limit 1
   ```

2. Убедись, что внешний вызов действительно может дать наблюдаемую ошибку
   OneScript. Сам факт вызова не является кандидатом на правило.
3. Зафиксируй решение в `probes/data/external-call-boundary-review.json`.

Для рассмотренной границы заполняй `CallerAssembly`, `CallerType`,
`CallerMember`, `Instruction`, `ExternalAssembly`, `ExternalType`,
`ExternalMember`, `Resolved`, `Status`, `Codes`, `Evidence` и `Note`.
У неразрешенной границы также обязательны `IlOffset` и `MetadataToken`.
`Defaults` применяй только к разрешенным внешним членам; точечная запись вызывающего члена
имеет приоритет.

`external-call-boundaries.json` обновляется только через `data refresh-source`
после обновления движка или по явному указанию пользователя.

### Исследования выполнения

- До повторного запуска используй сохраненные
  `probes/data/onescript-test-error-results.json` и
  `probes/data/base-type-error-matrix-results.json`.
- Обновляй их через `data refresh-runtime` только после обновления движка или
  его тестов.
- После обновления сравни JSON с предыдущей версией через Git. Новые записи
  `Unclassified` проверяй вручную, не считая их автоматически пробелами
  классификации.

Не коммить разовые `Проба*.os`, `candidate-*`, `runtime-candidate-*`, логи и
производные Markdown-отчеты.

## Код OneScript

- Следуй структуре ближайшего файла. Обычно это области
  `ОбработчикиСобытий`, `ПрограммныйИнтерфейс`,
  `СлужебныйПрограммныйИнтерфейс` и `СлужебныеПроцедурыИФункции`.
- Публичные методы размещай в `ПрограммныйИнтерфейс`, экспортные служебные
  методы модулей в `СлужебныйПрограммныйИнтерфейс`, внутренние методы в
  `СлужебныеПроцедурыИФункции`.
- Приватные переменные начинай с `_` и указывай справа их тип:
  `Перем _Таймаут; // Число`.
- Документируй добавленные или измененные публичные методы и конструкторы.
  Для параметров и результатов используй принятые блоки `Параметры` и
  `Возвращаемое значение`; для выбрасываемых ошибок добавляй `Исключения`.
- Называй функции кодов ошибок предметно и человекочитаемо.
- Не используй символы ё и длинное тире

## Тесты

- Имена тестов начинай с `ТестДолжен_` и формулируй предметно.
- Размещай тесты в области `Тесты`; вспомогательный код в
  `СлужебныеПроцедурыИФункции`.
- Тест правила обязан воспроизводить исходную ошибку, а не создавать похожий
  текст вручную. Для текстового правила добавляй близкий вариант, который не
  должен классифицироваться.

## Документация

- Поддерживаемые коды описывай в `docs/КодыНативныхОшибок.md`.
- Публичный API правил описывай в `docs/ПравилаНативныхОшибок.md`.
- Обновляй документацию вместе с правилом, если меняется код, назначение или
  область его применения.
- Инструкции по исследовательским данным храни только в `probes/README.md`.
